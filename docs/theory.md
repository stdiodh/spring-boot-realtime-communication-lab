# 이론 정리

## 1. 왜 이 개념이 필요한가

지금까지의 기능은 대부분 HTTP 요청이 들어오면 서버가 응답하는 구조였습니다. 이 방식은 게시글 조회, 로그인, 캐시 조회처럼 요청 단위가 분명한 기능에는 잘 맞습니다.

채팅이나 알림처럼 서버가 연결된 화면에 다시 메시지를 보내야 하는 기능은 요청/응답 한 번으로 설명하기 어렵습니다. 이번 시퀀스에서는 WebSocket과 STOMP를 이용해 연결을 유지하고, 서버가 topic으로 메시지를 다시 보내는 흐름을 확인합니다.

## 2. 기존 방식의 한계

HTTP만 사용하면 클라이언트가 새 요청을 보내야 서버의 새 상태를 확인할 수 있습니다. 사용자가 메시지를 보냈을 때 다른 화면이 바로 반응해야 한다면 반복 조회나 긴 대기 요청 같은 우회 방식이 필요해집니다.

이번 실습은 그런 우회 방식을 확장하지 않고, 연결을 유지한 뒤 서버가 다시 메시지를 전달하는 구조를 작게 경험하는 데 집중합니다.

## 3. 이번 시퀀스에서 선택한 접근

이번 시퀀스의 흐름은 아래 다섯 단계입니다.

1. 브라우저가 `/ws-chat` endpoint에 연결합니다.
2. 클라이언트가 `/app/chat.send`로 메시지를 보냅니다.
3. 서버 controller가 메시지를 받습니다.
4. 서버가 `/topic/chat`으로 메시지를 다시 보냅니다.
5. `/topic/chat`을 구독 중인 브라우저가 메시지를 화면에 표시합니다.

채팅방 관리, 메시지 저장, 읽음 처리, 사용자 세션 추적은 실시간 흐름을 이해한 뒤 확장할 주제입니다. 이번 단계에서는 endpoint, 전송 경로, 구독 topic, 메시지 DTO의 연결 관계를 먼저 잡습니다.

## 4. 핵심 개념

### HTTP

HTTP는 클라이언트 요청이 먼저 오고 서버가 그 요청에 응답하는 방식입니다. `PostController`, `AuthController` 같은 REST API에서 이 흐름을 볼 수 있습니다.

### WebSocket

WebSocket은 연결을 유지한 채 클라이언트와 서버가 메시지를 주고받을 수 있는 통신 방식입니다. 이번 코드에서는 `WebSocketConfig`의 endpoint 설정이 연결 진입점입니다.

### STOMP 경로

STOMP에서는 클라이언트가 서버로 보내는 경로와 클라이언트가 구독하는 경로를 구분합니다. 이번 실습에서는 `/app/chat.send`가 전송 경로이고, `/topic/chat`이 구독 topic입니다.

### 메시지 DTO

`ChatMessage`는 실시간으로 오가는 데이터 구조를 표현합니다. 이번 범위에서는 누가 보냈는지와 어떤 내용을 보냈는지를 확인할 수 있으면 충분합니다.

### topic broadcast

topic broadcast는 특정 topic을 구독 중인 클라이언트들에게 같은 메시지를 다시 보내는 흐름입니다. HTTP 응답처럼 요청한 한 명에게만 돌아가는 구조와 다릅니다.

## 5. 짧은 예제와 해설

아래 흐름을 말로 따라가면 이번 구현의 핵심을 확인할 수 있습니다.

```text
브라우저 연결 -> /app/chat.send로 전송 -> 서버 수신 -> /topic/chat으로 broadcast -> 구독 화면 수신
```

`WebSocketConfig.kt`는 연결 endpoint와 메시지 경로 규칙을 정합니다. `WebSocketController.kt`는 클라이언트가 보낸 메시지를 받아 topic으로 다시 보내는 지점을 담당합니다. `realtime-demo.html`은 사용자가 연결, 발행, 수신을 눈으로 확인하는 테스트 화면입니다.

## 6. 다음 구현으로 연결되는 지점

구현 단계에서는 코드를 많이 늘리는 것보다 아래 질문에 답할 수 있는 상태를 만드는 것이 중요합니다.

- `/ws-chat`, `/app/chat.send`, `/topic/chat`은 각각 어떤 역할인가요?
- HTTP controller와 WebSocket controller는 어떤 점이 다른가요?
- 메시지를 DB에 저장하지 않아도 실시간 흐름을 확인할 수 있는 이유는 무엇인가요?
- 테스트 페이지에서 connect, send, receive는 어떤 순서로 일어나나요?

다음 시퀀스에서 배포와 실행 환경을 다룰 때는 이런 연결이 실제 서버 환경에서 어떻게 유지되고 관찰되는지도 중요해집니다.
